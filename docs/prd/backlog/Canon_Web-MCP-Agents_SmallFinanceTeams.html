For leadership and judges: the problem, who has it, and what success looks like.

The problem today

01 · leaks

Context crosses the wall

A shared AI tool or a carelessly briefed agent shows a deal code name or deal terms to someone on the public side.

02 · wrong dose

Agents get too much or too little

Given everything, they're distracted and dangerous. Given nothing, they ask people to re-explain, or they guess.

03 · no proof

Nobody can show what each agent knew

When a regulator asks who saw what and when, the answer is spread across chat logs.

04 · stale walls

Walls change, agents don't

A deal is announced or dies, and running agents keep acting on old context.

Takeaways

borrow

Compliance software's vocabulary

Restricted list, watch list, wall-crossing with a reason and an expiry. Maya already thinks in these terms, so the UI uses them as-is.

borrow

Memory engines' handoff shape

Short facts with sources and two dates, served over MCP. Same tool names in every AI client.

differ

Filter before relevance

Glean copies the permissions apps already have. Canon owns the wall itself, and it runs before search, so walled facts are never even candidates.

simplify

One compliance officer, one screen

Big-bank tools assume a compliance department. Canon puts deals, requests, the feed and agents in one control room.

defer

Connectors and SSO

Real Slack, email and Jira connectors, SSO and billing are mid-size-firm features. The demo uses synthetic data.

avoid

"Memory everywhere" pitch

Supermemory and Mem0 already own that message. Canon's pitch is the wall.

03Product Solution

For leadership: the approach we chose, how it works, and the rules it follows.

Approaches considered

✓ recommended · approved

A · Filter-first walls

One store with a wall label on every fact. Plain code drops every fact the requester isn't cleared for before search and Jev run. Deny by default; only compliance approves crossings.

+ strongest leak guarantee, and one store makes an announcement a label change. − every query path must go through the filter.

alternative

B · A separate store per deal

One physically separate index per deal plus one public index. Each agent gets only the indexes it's cleared for.

+ easy to explain. − announcements and crossings mean copying data between stores, and the audit trail is split.

rejected · benchmark baseline

C · Walls enforced by the model

One shared store, and the model is told in its prompt to respect the walls.

− a prompt isn't a wall. This is the "shared memory" setup the benchmark expects to leak.

Business rules that never bend

RuleWhat it means in practice
Deny by defaultA fact reaches a person or agent only if code confirms they're cleared for its wall label.
Filter before searchWalled facts are removed before Moss or Jev see the request, so they can never show up as "relevant".
Jev never decides access aloneJev can flag, rank and pre-screen. Only compliance approves a crossing.
No agent can change permissionsNo MCP tool and no Droid sandbox can edit entitlements.
Labels only get stricter on their ownContent can make a fact more restricted, never less.
Neutral refusalsThe requester sees only the rule. Compliance sees the full reason. Watch-list names get a blander answer with no reason.
ThresholdsGenerous at save (the raw archive is the safety net), strict at handoff, and cautious on security: a "maybe" on confidentiality counts as yes.

The access predicate

Preconditions: the requester is authenticated by its client token, and quarantined text never became a fact (it waits as a quarantine review item until compliance releases it). Then one predicate decides:

canSee(principal, fact) =
     principal.desk == "compliance"
  || (  fact.wall != undefined                         // unlabeled → compliance only
     && (  fact.wall == "public"
        || deal(fact.wall).status == "announced"       // reads as public
        || cleared(principal, fact.wall) ) )

cleared(person, deal)  = exists Entitlement e: e.principal == person && e.deal == deal
                                           && (e.expires_at missing || e.expires_at > now)
cleared(agent, deal)   = agent.side == deal && cleared(agent.acts_for, deal)
                         // never more than the person it works for; no grant is made for an agent

requestAllowed(principal, task) =
     no restricted-list company (or deal alias) in task, unless cleared for that deal
  && no watch-list company in task, unless principal.desk == "compliance"
     // when it fails → NEUTRAL_REFUSALS[rule] + refusal AuditEvent + compliance alert

Announcing a deal changes its status, not each fact's label, so the predicate never changes and the labels keep their history. A terminated deal keeps its wall up; its agents are stopped by dispatch (an urgent cancel inbox item), not by the predicate.

A1 · Agent lanes. One lane per Droid, on its side of the wall. Each lane is also that agent's audit record.

Requirements · A1

  • Dispatch: a person types a task. Canon splits it into agent tasks and assigns each a side, builds each slice (permission filter first), and Claude writes a short brief.
  • Sandbox: one folder per agent holding only the files cleared for it. droid exec runs headless at a low permission level: create and edit files in its folder, nothing else. No network beyond Canon's MCP server.
  • Live routing: each task is a few short Droid runs (plan, then steps). Between runs, Canon checks the inbox and adds new facts to the next brief. Wall changes are urgent.
  • Exit check: before output leaves its side, code checks it for code names and restricted companies, and Jev checks for indirect references. A hit blocks the output, shows the red banner, and alerts compliance.
  • Terminated deal: the lane shows "Stopped · deal terminated", the next run is cancelled, and the folder is locked.
  • Gate: Droid runs finance tasks headless by 11:00 Sat, otherwise switch to a Claude Agent SDK runner (this drops the Factory track).
